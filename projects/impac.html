iMPAC: Programmable Matrix Accelerator & Low-Power RTL Design

Processing-element datapath architecture, control logic, systolic matrix streaming, and operation-aware operand isolation for dynamic switching-activity reduction in SystemVerilog.

01 Overview

iMPAC is a high-throughput, programmable hardware accelerator designed for matrix-multiplication operations and digital signal processing routines. Developed at the University of Tehran under the supervision of Prof. Zainalabedin Navabi, the project investigates microarchitectural optimizations across systolic processing arrays, reconfigurable datapaths, and power-aware RTL design techniques.

My work centers on the RTL implementation of individual Processing Elements (PEs), the control sequencing logic, functional testbench verification, and exploratory research into operation-aware operand isolation to eliminate redundant switching power in the datapath.

02 Problem Statement

Dense matrix multiplication is the primary computational bottleneck in edge neural networks, computer vision, and scientific computing. Standard arithmetic units in streaming datapaths suffer from severe energy waste because operand inputs continually toggle—even during cycles when the arithmetic block’s result is not utilized or when an identity/zero operation occurs.

In CMOS digital logic, dynamic power consumption is governed by:

P_dynamic = α · C_L · V_dd² · f_clk

where α represents the switching activity factor. Traditional clock-gating saves power in sequential flip-flops, but does not stop spurious switching activity from propagating through complex combinational add/sub and multiplier nets. Without fine-grained operand isolation, up to 30–50% of datapath energy is wasted on unobserved, discardable signal transitions.

03 Research Objective

  • Design a flexible, cycle-accurate Processing Element (PE) datapath in SystemVerilog capable of streaming multiply-accumulate (MAC) calculations.
  • Design a robust Control Sequencer FSM managing I/O streaming, weight buffering, and inter-PE handshakes.
  • Implement and evaluate operation-aware operand isolation on the add/sub datapath to selectively freeze inputs during dormant computation cycles.
  • Establish a rigorous SystemVerilog testbench verification environment with randomized test vectors, corner-case assertion checks, and automated scoreboarding.

04 Architecture

The iMPAC accelerator is organized around a grid of interconnected Processing Elements. Each PE houses arithmetic execution units, local register staging, and control gating logic:

Figure 1: Simplified microarchitecture of the iMPAC Processing Element showing upstream operand isolation.

Key Architectural Blocks:

  • Systolic PE Array: A scalable 2D network where data streams horizontally (activations) and vertically (accumulations), eliminating global memory read bottlenecks.
  • Operand Isolation Circuitry: Transparent latch-based or pre-multiplexer gates placed ahead of arithmetic logic. When an instruction does not execute an add/sub cycle, input operands are frozen, holding internal combinational node capacitance steady.
  • Integrated Control Sequencer: FSM tracking operation state (IDLE, LOAD_WEIGHT, COMPUTE, STREAM_OUT) and orchestrating pipeline register enables.

05 My Contributions

  • RTL Implementation: Authored SystemVerilog modules for the core PE datapath, operand isolation multiplexers, and local accumulator staging.
  • Control Logic & Sequencing: Built the FSM sequencer to regulate inter-PE handshakes and coordinate systolic data streaming without deadlocks.
  • Low-Power Exploration: Modeled operation-aware operand isolation on the add/sub datapath to measure switching activity reduction during inactive clock cycles.
  • Verification Environment: Constructed a comprehensive testbench in QuestaSim utilizing randomized matrix stimulus and automated self-checking scoreboards.

06 Implementation Details

The core operand isolation logic gates input changes when the computation flag is de-asserted. Below is a representative snippet of the operand isolation methodology:

pe_operand_isolation.sv (SystemVerilog) RTL Core 
// Operation-Aware Operand Isolation Block
module pe_operand_isolation #(
  parameter int WIDTH = 16
)(
  input  logic              clk,
  input  logic              rst_n,
  input  logic              op_active,      // Asserted when operation is executing
  input  logic signed [WIDTH-1:0] operand_in,
  output logic signed [WIDTH-1:0] operand_gated
);

  // Freeze input operand to zero (or hold previous state) during dormant cycles
  // to avoid charging/discharging internal adder capacitance.
  always_comb begin
    if (op_active) begin
      operand_gated = operand_in;
    end else begin
      operand_gated = '0; // Freeze datapath toggling
    end
  end

endmodule

07 Verification and Testing

The verification harness was built in QuestaSim / ModelSim to validate functional correctness and corner-case stability:

  • Randomized Stimulus: Over 10,000 randomized fixed-point matrix vectors were streamed through the pipeline to test full mathematical equivalence against a high-level Python software model.
  • Corner Cases Tested: Maximum positive/negative operand values, zero-multiplication, overflow saturation, and back-to-back reset events.
  • Assertion Coverage: SystemVerilog Assertions (SVA) used to monitor handshake protocol compliance and ensure operand isolation holds steady during stall cycles.

08 Results & Current Status

Note on Results: Functional verification is complete and passing with 100% testbench coverage. Quantitative switching power and silicon area trade-offs are currently under ongoing evaluation through synthesis in Synopsys Design Compiler. No fabricated silicon measurements are claimed.
